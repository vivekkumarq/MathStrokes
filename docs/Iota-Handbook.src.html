1  About the platform

Iota is a single-subject, high-stakes examination platform built around one idea: a result, once produced, must never move.

A teacher writes mathematics questions as LaTeX source, classifies them, and publishes them into a question bank. From that bank they compose timed tests. A student registers with a phone number, browses the published papers, and sits one: 25 questions, 60 minutes, one question at a time, with palette navigation, mark-for-review, and answers saved as they go. When the paper is submitted — by the student, or automatically when the clock expires — the server scores it from an immutable snapshot, ranks the student against everyone who sat the same paper, and releases the answer key and worked solutions for review.

1.1  The name

The platform is called Iota. The name is a double reference, and both halves are apt for a JEE Mathematics product. In Indian mathematics teaching the imaginary unit i = √−1 is routinely read aloud as "iota"; and ι is the Greek letter iota, proverbially the smallest quantity — the mark at the margin.

The mark on the cover reads at three levels. The dot above a curved stem is the letter ι itself. The faint tick to its right is a radical sign — √−1, the quantity "iota" names — carried at 50% opacity on purpose, so it reads as texture at large sizes and disappears cleanly at small ones. Below roughly 24 pixels the radical is dropped entirely and the dot and stem thicken; that reduction is the favicon. The brand gradient runs indigo #6366f1 through #4338ca to violet #7c3aed, and this handbook is set in the same indigo family.

The code still says mathstrokes — this is correct, not stale

Iota was previously called MathStrokes, and the product name has been changed everywhere it is user-facing. A number of identifiers deliberately have not been renamed, because renaming them would be a migration rather than a rebrand, and this handbook documents the system as it actually is. Expect to keep seeing the old name in:

  • the Java package com.mathstrokes.* and MathStrokesApplication;
  • the PostgreSQL database, role and JDBC URL — all mathstrokes;
  • the repository github.com/vivekkumarq/MathStrokes and the working directory MathStrokesTestPlatform;
  • the frontend CSS tokens --ms-* and the utility classes .ms-btn and .ms-card, which are shared across files and are not safe to rename piecemeal.

Every code sample, path and command in this handbook uses the real identifier, so it can be copied and run exactly as printed.

1.2  What makes it different

PropertyHow the platform guarantees it
Results are immutableEvery attempt copies the question text, options, answer key and marking configuration onto itself when it starts. Evaluation reads only that copy. A teacher who later rewrites a question, flips its key or archives it cannot move a mark already awarded.
The server owns the clockexpires_at is written once when the attempt starts and is never extended. The browser countdown displays the server arithmetic; it is not a source of truth.
The answer key cannot leakThe payload a live attempt returns has no correctness field and no solution text — it is a structurally different type from the review payload, so the key cannot escape through a forgotten filter.
Nothing is lost to a bad connectionEach autosave carries a monotonic sequence number. A write arriving out of order is a late packet: it is discarded rather than allowed to overwrite newer work, and the response returns the state the server actually holds.
Abandoning still gets markedA scheduled sweep finalises attempts whose time has run out, scoring the answers already saved. Closing the tab does not void the paper.
Scoring is exactAll marks are NUMERIC / BigDecimal, never floating point, so partial-marking arithmetic is precise.

2  Roles and what each can do

There are exactly two roles. There is no role hierarchy and no third tier.

/api/profile		 Subjects and chapters, the question bank, marking schemes, test creation and publication, the student roster, and analytics.

Examination candidate		 /api/tests
/api/attempts/**
/api/me/performance

/api/catalog/**		 Browsing published tests, sitting papers, reviewing their own finished attempts, and tracking their own performance.
How the boundary is enforced

Path level: /api/admin/** requires ROLE_ADMIN in SecurityConfig; student routes carry @PreAuthorize. Object level — and this is the real guard — no endpoint accepts a student id. The caller is always derived from the security context, and every attempt is loaded through a single method that proves ownership. A student requesting another student's attempt receives 403.

Registration cannot escalate

POST /api/auth/student/register always creates a student; the role is not a field on the request and cannot be chosen. Additional administrators are created by seeding, not through the public API.

Deliberately not present

The platform contains no AI, OCR, handwriting recognition or LLM integration; no file or object storage and no image upload on questions (mathematics is LaTeX text, so there are no diagrams to store); no cache, message queue, microservices or Kubernetes; no bulk question import endpoint; no email or SMS; and no OAuth, sessions or cookies — JWT bearer only. Each of these is a recorded decision, not an oversight.

4.2  Prerequisites for a developer machine

  • JDK 21 — java -version should report 21.x
  • Node.js 20+ and npm
  • PostgreSQL 17 running locally, or any reachable PostgreSQL 14+
  • Git

Maven is not required — the repository ships the Maven wrapper (./mvnw, or mvnw.cmd on Windows).

4.3  Why these choices

The stack is deliberately conservative. A first release has to be cheap to run and easy to reason about, so the project avoids microservices, Kafka, Redis and Kubernetes entirely. One Spring Boot process and one PostgreSQL database serve the whole platform. PostgreSQL earns its place beyond storage: JSONB holds marking configuration without a migration per rule, partial unique indexes enforce invariants the application would otherwise have to police under concurrency, and a window function computes the entire leaderboard in a single pass.

5  System architecture

5.1  Shape of the system

Angular 22 (standalone, zoneless, signals) | | HTTPS / REST, JWT bearer v Spring Boot 3.5 (modular monolith, one deployable) | +-- auth registration, login, rotating refresh tokens, recovery +-- user accounts, roles, student roster +-- catalog subjects and chapters +-- question the LaTeX question bank +-- marking marking schemes and evaluation strategies +-- exam tests, publication, question selection +-- attempt sitting a paper: snapshot, autosave, submit, evaluate +-- ranking leaderboards and percentiles +-- analytics dashboards and question quality | v PostgreSQL 17

Each module owns its own controller / service / repository / entity / dto / mapper layers. Controllers carry no business logic, and no JPA entity is ever serialised to a client — every response is a record DTO. The module boundaries are real seams along which services could be extracted later if that ever becomes necessary; it is not necessary now.

5.2  Where decisions live

Every business decision is server-side. The browser is a rendering layer: it displays the server countdown, submits selections, and repaints from the server acknowledgement. Nothing about scoring, timing, eligibility or ranking is computed in the client, and the client is never sent data it should not be able to see.

5.3  Request path for an authenticated call

Browser | Authorization: Bearer <accessToken> v CORS filter origins from CORS_ALLOWED_ORIGINS v JwtAuthenticationFilter validates signature, expiry and the token TYPE claim v populates SecurityContext with UserPrincipal Authorization path rules (/admin/** = ROLE_ADMIN) + @PreAuthorize v Controller @Valid on the request record -> 400 with fieldErrors v Service business rules, ownership checks, transactions v Repository / Hibernate -> PostgreSQL v Mapper -> record DTO -> JSON nulls omitted, entities never serialised

5.4  Background work

JobCadencePurpose
Attempt expiry sweepevery 30 secondsFinalises attempts whose deadline has passed, scoring the answers already saved, so an abandoned paper is still marked.
Refresh-token purgedaily, 03:30Deletes refresh tokens that expired more than 30 days ago.

6.2  Backend module anatomy

Every module follows the same six-layer shape, so any module reads like any other:

controller/HTTP surface only — routing, @Valid, status codes, OpenAPI annotations. No business logic.
service/Business rules, transaction boundaries, ownership checks, orchestration.
repository/Spring Data interfaces plus JPA Specifications for dynamic filtering.
entity/JPA entities extending BaseEntity (id, createdAt, updatedAt). Never serialised.
dto/Java records. Request records carry Bean Validation annotations; response records carry the wire shape.
mapper/Entity to DTO translation. The only place the two representations meet.

6.3  Frontend anatomy

core/auth/AuthService (HTTP), AuthStore (signals-based session state), TokenStorage.
core/http/authInterceptor attaches the bearer token; TokenRefreshCoordinator serialises concurrent refreshes so one 401 cannot trigger a stampede.
core/guards/authGuard, roleGuard(...), guestGuard, landingGuard. Convenience only — the backend enforces authorisation for real.
core/models/Enums and interfaces mirroring the backend contract, kept in lockstep by hand until the OpenAPI document is used for generation.
shared/math/latex-renderer and the MathContent component — the single place KaTeX is invoked.
features/One folder per feature, each lazily loaded. The exam runner pulls in KaTeX and the results screen Chart.js; neither belongs in the bundle a student downloads to reach the login screen.

Three independent axes

Exam pattern, difficulty and question type are orthogonal. A JEE Advanced question can be EASY, and a JEE Main question can be HARD. The input control a student sees — radio versus checkbox — follows question_type, never exam_pattern, because a JEE Advanced paper may contain single-correct questions.

7.6  Attempts and the snapshot

test_attempts holds the lifecycle (started_at, expires_at, submitted_at, evaluated_at) and, once evaluated, the whole result: score, max_score, negative_marks, the four outcome counts, accuracy, attempt_rate, time_taken_seconds, rank_position, total_candidates and percentile. A partial unique index on (student_id, test_id) WHERE status = 'ACTIVE' means the database itself guarantees one live attempt per test, so two concurrent start requests cannot both succeed.

The snapshot — the single most important design element

attempt_questions stores question_version, the stem, the solution, the difficulty, the type, marking_scheme_name, marking_config JSONB and max_marks. attempt_question_options stores each option key, content, order and is_correct — the answer key as it stood at snapshot time. Evaluation reads only these tables. The FK back to questions exists for analytics and is never followed for content or correctness.

8  Adding a question — full walkthrough

This is the core administrator procedure. It is given twice: first as the screen-by-screen flow an administrator follows, then as the exact API contract behind it.

8.1  Before you start

  • You must be signed in as ROLE_ADMIN. Signing in lands you on /admin.
  • The chapter you want to file the question under must already exist and be active — see section 11.
  • An active marking scheme must exist for the (exam pattern, question type) pair you intend to use, or publication will fail. The four seeded schemes cover every combination out of the box.

8.2  The screen flow

1

Open the question bank

From the admin shell, go to Question bank — route /admin/questions.

The grid lists questions newest-updated first, 20 to a page, showing chapter, exam pattern, difficulty, type, a preview of the stem, status, option count and revision. Filter by subject, chapter, exam pattern, difficulty, question type and status, or search free text across the stem and solution. Reset clears every filter and returns to page 1.

2

Start a new question

Click New question — route /admin/questions/new.

The editor opens with four blank options already laid out and labelled A, B, C, D, and with sensible defaults selected: exam pattern JEE_MAIN, difficulty MEDIUM, question type SINGLE_CORRECT.

3

Classify the question

Set the four classification fields at the top of the form:

FieldValuesNotes
ChapterAny active chapterRequired. The subject is derived from it automatically — there is no separate subject field.
Exam patternJEE_MAIN, JEE_ADVANCEDRequired. Selects which marking scheme applies.
DifficultyEASY, MEDIUM, HARDRequired. Used by the test difficulty blueprint. Independent of exam pattern.
Question typeSINGLE_CORRECT, MULTIPLE_CORRECTRequired. Decides radio versus checkbox for the student, and which evaluation strategy scores it.

Switching the type to single-correct collapses any extra correct selections down to the first, so the form cannot sit in a state the server would reject.

4

Write the question stem

Type the stem into Question content as LaTeX and plain text. A live KaTeX preview renders beside the textarea as you type. Maximum 20,000 characters; required. 

Solve for $x$:

$$x^2 - 5x + 6 = 0$$

Blank lines are meaningful paragraph breaks and are preserved verbatim. See section 10 for the full LaTeX reference.

5

Fill in the options

Four option rows are provided, labelled A to D. Each row takes LaTeX content — required, up to 5,000 characters — and has its own live preview. displayOrder is taken from the row position, so the A–D order stays consistent without your having to manage it.

Option labels must be a single uppercase letter and must be unique within the question. A question needs between 2 and 10 options.

6

Mark the correct answer

Tick the correctness control on each option that is part of the answer key.

  • SINGLE_CORRECT — the form behaves as a radio group: selecting one option clears the others.
  • MULTIPLE_CORRECT — any number may be ticked, but not all of them (see step 9).
7

Add the worked solution (optional but recommended)

Solution content takes LaTeX up to 20,000 characters, with its own live preview. It is shown to students only on the answer-review screen, after their attempt is finalised — never during a live paper.

Left empty, the field is omitted from the request rather than sent as an empty string.

8

Save as a draft

Click Save. The question is created with status DRAFT and you are navigated to its edit route, /admin/questions/{id}.

Draft rules are deliberately permissive so half-finished work can be saved. Only these are checked on save: content not blank, option labels unique and single uppercase letters, 2–10 options, length caps, and a markup guard (see the box below).

9

Publish

Click Publish. Publication applies the strict rules, and only a question that passes them can enter the bank that test generation draws from:

  • At least two options.
  • SINGLE_CORRECT must have exactly one correct option — the error names the count it actually found.
  • MULTIPLE_CORRECT must have at least one correct option, but not all of them — an all-correct question is unanswerable.
  • Option labels must be unique.
  • An active marking scheme must exist for the (exam pattern, question type) pair. This is checked at publish time so it fails here rather than at a student first click.

On success the status becomes PUBLISHED and published_at is stamped. The question is now eligible for test generation.

The content safety guard

On every save the server rejects content containing <script, <iframe, <object, <embed, javascript: or an inline on…= event handler. The check is deliberately narrow: $a < b$ is ordinary mathematics and is accepted. The client is the first line of defence — it escapes everything outside the maths delimiters and runs KaTeX with HTML trust disabled — and this is defence in depth behind it.

8.3  The API contract behind the form

POST /api/admin/questions  ·  ROLE_ADMIN  ·  201 Created

{
  "chapterId": 3,                              // required — subject is derived from it
  "examPattern": "JEE_MAIN",                   // required — JEE_MAIN | JEE_ADVANCED
  "difficulty": "MEDIUM",                      // required — EASY | MEDIUM | HARD
  "questionType": "SINGLE_CORRECT",            // required — SINGLE_CORRECT | MULTIPLE_CORRECT
  "questionContent": "Solve $x^2-5x+6=0$",     // required, <= 20000 chars, LaTeX source
  "solutionContent": "...",                    // optional, <= 20000 chars
  "markingSchemeId": null,                     // optional override; null = resolve active scheme
  "options": [                                 // required, 2..10 entries
    { "optionKey": "A", "content": "$x=2$ or $x=3$",   "displayOrder": 0, "isCorrect": true  },
    { "optionKey": "B", "content": "$x=-2$ or $x=-3$", "displayOrder": 1, "isCorrect": false },
    { "optionKey": "C", "content": "$x=1$ or $x=6$",   "displayOrder": 2, "isCorrect": false },
    { "optionKey": "D", "content": "$x=-1$ or $x=-6$", "displayOrder": 3, "isCorrect": false }
  ]
}

Field-by-field validation

FieldRequiredRule and message
chapterIdyes@NotNull — "Chapter is required". Must resolve to an existing chapter.
examPatternyes@NotNull — "Exam pattern is required".
difficultyyes@NotNull — "Difficulty is required".
questionTypeyes@NotNull — "Question type is required".
questionContentyes@NotBlank, @Size(max=20000). Trimmed on write.
solutionContentno@Size(max=20000).
markingSchemeIdnoWhen absent, the active scheme for (pattern, type) is resolved at evaluation time.
optionsyes@NotEmpty, @Size(min=2, max=10) — "A question must have between 2 and 10 options".
options[].optionKeyyes@Pattern("^[A-Z]$") — "Option label must be a single uppercase letter". Uppercased and de-duplicated on write.
options[].contentyes@NotBlank, @Size(max=5000). Trimmed on write.
options[].displayOrderno@PositiveOrZero. Defaults to the array index.
options[].isCorrect—Boolean, defaults false. This is the answer key.
Validation is two-tiered

Save-time rules apply to drafts too and are permissive. Publish-time rules are strict, and are enforced both on POST /{id}/publish and on any update to an already-published question — so a published question cannot be edited into an invalid state while remaining published.

Errors bind straight to the form

Every validation failure reports fieldErrors[].field as the JSON property name of the request body — questionContent, solutionContent, options, options[2].content — so the Angular form binds a server message onto the exact input that caused it, with no translation layer.

9  Question lifecycle

POST /admin/questions | v [ DRAFT ] <-------------------+ | | POST /{id}/publish | | POST /{id}/draft (strict rules) v | [ PUBLISHED ] ------------------+ | | POST /{id}/archive v [ ARCHIVED ] read-only, terminal (also reachable from DRAFT)
StateReached byMeaning
DRAFTCreation, or revertEditable freely under permissive rules. Invisible to test generation.
PUBLISHEDPOST /{id}/publishEligible for test generation. Still editable, but every edit must continue to satisfy the strict publish rules.

9.1  Editing a published question

Editing a question that has already been used in a live examination is allowed and safe. Each attempt holds its own snapshot of the content, options and answer key, so no historical result can move. What changes is the version number, which increments on every persisted write and is recorded on any future attempt snapshot that uses the question.

version also serves as a Hibernate optimistic lock, so two administrators editing the same question cannot silently overwrite each other — the second write fails rather than winning by accident.

Verified end to end

An automated check rewrites a question stem, flips its answer key and archives it, then re-reads a student existing attempt: the score, the counts, the per-question marks, the stem and the key all come back byte-identical.

9.2  There is no delete

The API exposes no hard delete for questions. Archive is the terminal state, because attempts, per-question results and analytics all reference the row. Removing it would break referential integrity and destroy history; the foreign keys are declared ON DELETE RESTRICT to make that impossible rather than merely discouraged.

10  Writing questions in LaTeX

The teacher types LaTeX; the browser renders it with KaTeX; the source is what gets stored.

Admin types LaTeX -> KaTeX live preview -> saved as SOURCE in PostgreSQL | KaTeX renders <- student fetches the source

Rendered HTML is never persisted. The stored value stays the single source of truth, cannot carry markup into a page, and can be re-rendered by a different renderer later without a migration.

Content is LaTeX and plain text, never HTML. The server refuses to save content containing <script, <iframe, <object, <embed, javascript: or an inline event handler. The check is narrow by design so ordinary mathematics is never caught by it — $a < b$ saves without complaint.

10.5  Authoring advice

  • Watch the preview. It is the same renderer the student will see. If it does not render for you, it will not render for them.
  • Keep options parallel. Options that differ only in the value being tested read more fairly than options that differ in form.
  • Write the solution while the question is fresh. It is the only thing a student has to learn from after the paper, and it costs far more to reconstruct later.
  • Derive the key, do not assume it. The seeded sample questions were generated from known integer roots rather than typed by hand, precisely so every answer key agrees with its own worked solution.

15  The marking engine

Marks are computed on the server, from a configuration stored as JSON, by one strategy per question type. Nothing about scoring is hardcoded in a controller, and nothing is computed in the browser. 

public interface EvaluationStrategy {
    QuestionType supportedType();
    AnswerEvaluation evaluate(Set<Long> correctOptionIds,
                              Set<Long> selectedOptionIds,
                              MarkingConfig config);
}

Implementations are discovered as Spring beans and indexed by the type they support, so adding a question type means adding one class and one marking-scheme row — the evaluation pipeline itself does not change.

15.1  Single correct

SituationResult
The key is selectedfullCorrectMarks, CORRECT
Anything else, including more than one selectionwrongMarks, INCORRECT
Nothing selectedunansweredMarks, UNANSWERED

15.2  Multiple correct — the rule ladder, in order

SituationResult
Nothing selectedunansweredMarks, UNANSWERED
Any option outside the key selectedwrongMarks, INCORRECT
The key selected exactlyfullCorrectMarks, CORRECT
A strict subset of the key, nothing wrongpartial credit, PARTIALLY_CORRECT
Order matters

The wrong-selection check comes before partial credit. That single ordering is what makes the JEE Advanced scheme come out right: a student who picks two correct options and one wrong one scores −2, not +2.

Under PER_CORRECT_OPTION, the award is marksPerCorrectOption × matchedCount, capped at maxPartialMarks. With the seeded JEE Advanced configuration this reproduces the official scheme exactly: +4 for the exact key, +1 per correct option capped at +3, −2 for any wrong selection, 0 for no attempt.

15.3  Reported metrics

accuracy    = correct / attempted × 100      (0 when nothing was attempted)
attemptRate = attempted / total     × 100

A partially correct answer counts as attempted but not correct, so accuracy reads as the share of attempts that were fully right.

15.4  Precision

Marks are NUMERIC(8,2) in the database and BigDecimal in Java, throughout. Floating point is never used for a mark. With partial credit in play, a paper is a long chain of additions of values like 1.00 and −2.00, and binary floating point would accumulate error that eventually shows up as a wrong total on somebody result page.

15.5  Adding a new question type

  1. Add the constant to the QuestionType enum.
  2. Implement an EvaluationStrategy bean for it.
  3. Insert a MarkingScheme row for each exam pattern it applies to.
  4. Extend QuestionValidator with its publish rule.

Nothing else changes. Only types that have a registered strategy are declared in the enum, so the API never advertises a type that would fail at runtime.

16  Ranking, percentile and metrics

16.1  The cohort

Students are compared only when they sat the same paper. A test whose questions are drawn per attempt is not ranked at all. Only FIXED_SET tests — whose questions are materialised once at publication — carry rankingEnabled: true.

16.2  One position per student

If a test allows several attempts, only a student best attempt is placed, so sitting a paper twice cannot occupy two positions on the board.

16.3  Ties

RANK semantics: 1, 2, 2, 4. Genuinely tied students share a position and the next rank skips accordingly. Ties break on, in order:

  1. Total score
  2. More correct answers
  3. Fewer incorrect answers
  4. Faster completion
  5. Earlier submission

16.4  Percentile

percentile = 100 × (candidates scoring at or below you) / total candidates

This follows the NTA definition and is computed on raw score alone, so a tie-break on time does not move it. The topper is at 100.00.

16.5  Recalculation

The whole cohort is recomputed whenever an attempt is evaluated, in one PostgreSQL window-function pass. A student who finishes first therefore sees a real position immediately, and that position can move as later candidates finish — which is what "rank among everyone who sat this paper" has to mean while the paper is still open. Once a test is CLOSED, no new attempts can start and the board settles.

Client guidance

Because a rank shown at submission is a snapshot, a client should re-fetch the result rather than cache the rank indefinitely.

17  The student journey

1 GET /api/tests browse published papers; each says whether it can be started and whether one is in flight 2 POST /api/attempts start OR resume; the server draws the paper, SNAPSHOTS every question, writes started_at and expires_at, returns all 25 questions at once 3 PUT /api/attempts/{id}/answers autosave, checked four ways 4 POST /api/attempts/{id}/submit manual, or automatic at expiry 5 GET /api/attempts/{id}/result score, rank, percentile, metrics 6 GET /api/attempts/{id}/review answer key and worked solutions

17.1  Every autosave is checked four ways

  1. The attempt belongs to the caller.
  2. It is still ACTIVE.
  3. The server clock says it has not expired.
  4. The question belongs to that attempt.

17.2  Behaviours that matter

BehaviourHow it works
Refreshing changes nothingCalling POST /attempts while an attempt is live resumes it: same questions, same order, same deadline. It never redraws the paper or restarts the clock.
The clock is the serverEvery attempt response carries timing: { serverTime, startedAt, expiresAt, remainingSeconds, expired }. remainingSeconds is the server own arithmetic; serverTime lets the client correct for clock drift instead of trusting the browser.
Abandoning still gets markedThe expiry sweep finalises attempts whose time ran out, scoring the answers already saved.
Nothing is lost to a bad connectionEach save carries a monotonic clientSequence, incremented once per attempt rather than per question. A write with an older sequence is discarded, accepted: false is returned, and the response carries the newer stored state so the client reconciles instead of guessing.
Submission is idempotentAn attempt already submitted, or auto-submitted by the sweep, returns its result with 200 rather than an error — so the auto-submit race never needs a conflict screen.
The key is absent, not hiddenThe live-attempt DTO has no correctness field and no solution text. They exist only on the review type.

17.3  Palette states

Each question carries one of five states, persisted server-side so the palette survives a refresh: NOT_VISITED, NOT_ANSWERED, ANSWERED, MARKED_FOR_REVIEW, ANSWERED_AND_MARKED_FOR_REVIEW. The refreshed 25-entry palette and the server clock come back with every save, so the navigator and the countdown update from the same response — no second call.

18.3  Tokens

{
  "accessToken": "eyJ...",
  "refreshToken": "eyJ...",
  "tokenType": "Bearer",
  "expiresInSeconds": 900,
  "user": { "id": 3, "fullName": "...", "phoneNumber": "...",
            "roles": ["ROLE_STUDENT"], "enabled": true, "createdAt": "..." }
}
  • The access token is a short-lived JWT — 15 minutes by default — sent as Authorization: Bearer.
  • The refresh token is persisted as a SHA-256 digest with constant-time comparison, and is rotated on every use: presenting it revokes it and issues a replacement. Default lifetime 7 days.
  • Presenting an already-rotated refresh token is treated as a stolen credential being replayed and revokes every session for that account.
  • Every token carries a type claim, so an access token cannot be replayed as a refresh token or as a password-reset authorisation.
  • Refresh returns a whole new pair — replace both values wholesale, never merge.

18.4  Password storage

Passwords and security answers are hashed with BCrypt at strength 12, so a database leak exposes neither. Neither hash is mapped into any DTO, so neither can be serialised into a response by accident.

18.5  Anti-enumeration

  • Login cannot distinguish a wrong password from an unknown account — both return AUTHENTICATION_FAILED. Render one neutral message.
  • Recovery cannot be short-circuited: knowing a phone number returns nothing but the question. Only a correct answer mints a reset token.
  • The reset token authorises exactly one password change, and this is enforced without storing any server-side state: the token carries a fingerprint of the password hash it was minted against. Completing a reset changes the hash, the fingerprint stops matching, and a replayed token is refused even inside its ten-minute lifetime. Applying it also revokes every existing session for the account.
  • Login, the security-answer challenge and recovery initiation are rate limited per identifier; registration is throttled per client address.
  • Paginated endpoints cap page size at 100, so a single request cannot be used to drain a table.

18.6  Transport and hardening

  • Stateless sessions; CSRF disabled because there are no cookies to forge against.
  • CORS restricted to CORS_ALLOWED_ORIGINS, with Authorization exposed.
  • Stack traces and framework messages are never included in error responses.
  • rejectedValue is withheld for password, confirmPassword, newPassword, currentPassword, securityAnswer, resetToken, refreshToken and accessToken — so a submitted password is never written into a response body or a network log.
  • Swagger and the OpenAPI document are disabled on the prod profile by default.

23  Database and migrations

Flyway owns the schema. Hibernate is set to validate and will refuse to start if the mapping and the schema disagree — so a drift between the two is caught at boot rather than at the first query that touches the changed column.

MigrationContents
V1__initial_schema.sql17 tables, constraints and indexes
V2__seed_reference_data.sqlRoles, Mathematics, the first 17 chapters, 4 marking schemes. Idempotent.

V4__seed_full_question_bank.sqlThe remaining 11 chapters and 1,456 further questions
V5__seed_chapter_tests.sql56 published chapter papers — 28 chapters × 2 exam patterns
Why the bank is a migration, not a script

A deployed instance builds its database from migrations alone. Content created by POSTing to a running server exists only on the machine that received the POSTs, so seeding through Flyway is the only way a deployed site has a question bank at all. The payload in V4 is dollar-quoted JSON rather than ordinary SQL string literals: the content is LaTeX, dense with backslashes and $$ display-maths delimiters, and escaping that into normal literals is a reliable way to corrupt a macro or terminate a string early.

Migrations are never edited once applied — add a new V4__… instead. To start over locally: 

DROP DATABASE mathstrokes;
CREATE DATABASE mathstrokes OWNER mathstrokes;

On a fresh database the application creates:

  • Mathematics and its 28 chapters — 17 from V2 (Relations and Functions, Complex Numbers, Quadratic Equations, Sequences and Series, Permutations and Combinations, Binomial Theorem, Matrices, Determinants, Limits, Continuity and Differentiability, Applications of Derivatives, Integrals, Differential Equations, Vectors, Three Dimensional Geometry, Probability, Statistics) and 11 more from V4.
  • Four marking schemes, one per (exam pattern, question type) pair.

The sample questions were generated from known integer roots rather than typed by hand, so every answer key agrees with its own worked solution. Both runtime seeders skip silently if an admin or any test already exists, so restarting the application never overwrites real data.

The seeded papers allow five attempts, not one

Every V5 paper is FIXED_SET — the 25 questions are drawn once and pinned, which is what makes the cohort comparable and is the only mode under which ranking is enabled. But max_attempts_per_student is 5 rather than 1, because these are demonstration papers meant to be re-sat while exploring the marking schemes. A real examination should use 1.

25  Deployment

25.1  Current status

Live, with the API pending

The frontend is deployed and public at https://mathstrokes.netlify.app. The backend is not yet deployed: the site loads, but it cannot authenticate, because /api/* proxies to a placeholder until a backend host exists. Everything behind a sign-in is therefore unreachable on the public site today.

Note that the URL still carries the former product name. The rename to Iota did not move the Netlify site, so the hostname is expected to read mathstrokes until somebody deliberately migrates it.

25.2  It is three pieces, not one

This is the part a reader is most likely to get wrong. Netlify cannot run a JVM, so the Angular bundle and the Spring Boot service are hosted separately and stitched together by a proxy rather than deployed as one unit.

Browser | v Netlify serves the built Angular bundle (static files) | /api/* -- proxied by netlify.toml v Backend container Spring Boot, on a host that runs containers | v Managed PostgreSQL Flyway migrates on first boot
ComponentApproach
Frontendnpm run build produces static files. Served by Netlify (any static host or CDN would do).
The proxynetlify.toml forwards /api/* to the backend. Because the browser only ever calls its own origin, there is no CORS in production at all — the CORS_ALLOWED_ORIGINS setting matters for local development and for any client that bypasses the proxy.
BackendA container built from backend/Dockerfile, deployable to any host that runs containers, including free tiers. Configured entirely through environment variables.
DatabaseAny managed PostgreSQL. Flyway migrates on first boot.
Gotcha: every URL returns 401 behind a "Login Redirect" page

If a healthy Netlify deploy answers 401 on every URL, including the site root, the cause is almost certainly SSO site protection enabled on the Netlify account — not anything in the build. Nothing in the deploy log hints at it and the build itself reports success. Fix it by setting sso_login and account_sso_login to false. This cost twenty minutes once; it is written down so it costs nobody twenty minutes again.

25.3  Production checklist

  • SPRING_PROFILES_ACTIVE=prod
  • A strong JWT_SECRET from a secret store, never from source control
  • CORS_ALLOWED_ORIGINS set to the real frontend origin
  • SEED_ENABLED=false once the first admin exists
  • SWAGGER_ENABLED left off
  • The seeded admin password changed
Expect one forced sign-out at the rebrand deploy

The browser storage keys moved from mathstrokes.auth.* to iota.auth.*. Existing sessions cannot be read under the new keys, so every signed-in user is signed out exactly once when that build goes live. It happens a single time, not on subsequent deploys, and no server-side data is affected — but it is worth announcing rather than letting students discover it mid-revision.

On the prod profile, Flyway clean is disabled, stack traces and binding errors are excluded from responses, and root logging drops to WARN.

27  Architecture decisions

Twelve decisions are recorded in full, with rationale and cost, in docs/ARCHITECTURE.md. In summary:

#DecisionWhy
1A modular monolith, not microservicesOne deployable is cheap to run and easy to reason about; the module seams remain available if extraction is ever needed.
2Attempts carry an immutable snapshotThe only way to guarantee a historical result cannot move when a question is edited.
3The server owns the clockA client clock is attacker-controlled; the countdown is a display, not a source of truth.
4Ranking compares only identical papersTwo randomly drawn papers are different examinations; comparing them is meaningless.
5Marking is configuration plus a strategyA new rule needs a row, not a release; a new type needs one class.
6Money-like arithmetic uses BigDecimalPartial marking accumulates error under floating point and eventually shows a wrong total.
7Refresh tokens rotated and stored hashedA leak cannot be replayed; a replayed token is detected and revokes the account sessions.
8Ownership is derived, never acceptedNo endpoint takes a student id, so no endpoint can be talked into acting as someone else.
9The answer key is structurally absentA different type cannot leak a field it does not have; a filter can be forgotten.
10Idempotent submissionThe auto-submit race needs no conflict screen. The first implementation deadlocked; the fix is documented.
11Flyway owns the schemaHibernate validates against it and refuses to start on drift.
12Known limitations recorded honestlySee section 28.

28  Limitations and roadmap

28.1  Known limitations

LimitationImpact and workaround
The OpenAPI document marks nothing as requiredJava records carry no nullability metadata. Do not infer optionality from the generated spec — use the omit-null rule and the documented field tables instead.
Nulls are omitted, not sentOptional fields are absent from responses. Any generated client must model them as optional or it will misread a valid payload.
Rate limiting is in-process and per-instanceHonest for a single-node deployment; behind a load balancer it would need a shared store.
No bulk question importQuestions are created one at a time via the API, or seeded through a Flyway migration.
No image upload on questionsMathematics is expressed as LaTeX, so there is nothing to store. A question needing a diagram cannot currently be authored.
Only two question typesSINGLE_CORRECT and MULTIPLE_CORRECT. Only implemented types are declared, so the enum never advertises something that would fail at runtime.

28.2  Roadmap, in rough priority order

  • More question types — NUMERICAL, INTEGER, MATCHING, ASSERTION_REASON, COMPREHENSION. The extension point is real: enum constant, one strategy bean, one marking-scheme row.
  • More subjects — Physics and Chemistry need no schema change; subjects and chapters are already generic and the client reads them from the API.
  • OTP recovery — the recovery flow is three separate steps precisely so an OTP challenge can replace the security answer without touching the reset step.
  • Required-field metadata in the OpenAPI document — @Schema(requiredMode = REQUIRED) across the response DTOs.
  • Distributed rate limiting — a shared store behind a load balancer.
  • Question versioning as first-class history — attempts already snapshot everything they need, so a teacher-facing revision history would be purely additive.
  • Sub-chapters, bulk question import, and scheduled test windows.
